# Yui

Yui is a desktop-first flashcard app for language learning. The repository contains an Angular frontend and a Spring Boot REST API with PostgreSQL persistence for decks and flashcards. Study scheduling uses FSRS-6, and Gemini can suggest Polish translations, English examples, and Polish mnemonics while creating a card.

## Requirements

- Node.js 22.12 or newer (Angular 21 requirement)
- npm 10 or newer
- Java 21 or newer and Maven 3.6.3 or newer
- Docker Compose for the local PostgreSQL setup (or an existing PostgreSQL 17+ server)

## Run the frontend

```bash
cd frontend
npm ci
npm start
```

Open `http://localhost:4200/`. To create a production build, run `npm run build`; run the frontend tests with `npm test` (both commands from `frontend/`).

## Run the backend

The app expects a database and login role named `wordstead` on port `5432`. They are already set up on this development machine. For a fresh local PostgreSQL installation, connect as an administrator with `psql -h localhost -U postgres -d postgres` and run these commands if the role and database do not already exist:

```sql
CREATE ROLE wordstead LOGIN;
CREATE DATABASE wordstead OWNER wordstead;
\password wordstead
```

The psql password command prompts twice and stores a password hash instead of a plaintext password in SQL history. Set that password as `DATABASE_PASSWORD` in the IntelliJ run configuration for `YuiApiApplication`; the repository does not contain it.

To start the backend from PowerShell without putting the password in shell history, enter it at the hidden prompt:

```powershell
$secure = Read-Host 'PostgreSQL password' -AsSecureString
$ptr = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($secure)
try {
  $env:DATABASE_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($ptr)
  Set-Location backend
  mvn spring-boot:run
} finally {
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($ptr)
  Remove-Item Env:DATABASE_PASSWORD -ErrorAction SilentlyContinue
}
```

If you prefer Docker Compose instead of the installed PostgreSQL service, copy `.env.example` to `.env` and run `docker compose up -d database` from the repository root. Do not run both database setups on the same port.

The API starts on port `8080`. Check `http://localhost:8080/api/health`; it should return `{"status":"UP","service":"yui-api"}`. Run the backend integration tests with `mvn test` from `backend/`.

### Gemini flashcard suggestions

The card form asks the backend for suggestions when you leave the English word field. You can also request them with **Generate with AI**. Suggestions fill only blank translation, example, and mnemonic fields, so text you have already entered is preserved. The app uses the Gemini `gemini-3.5-flash-lite` model by default and sends requests from Spring Boot; the browser never receives the API key.

Set `GEMINI_API_KEY` in the IntelliJ run configuration environment variables for `YuiApiApplication`. Set `GEMINI_MODEL` to `gemini-3.5-flash-lite`, or omit it to use the default. For PowerShell, set the variable in the current session before starting Maven: `$env:GEMINI_API_KEY = 'your-new-key'`. Do not commit local credentials. The API key that was pasted into the chat should be revoked and replaced before use.

The backend endpoint is `POST /api/ai/flashcard-suggestions` with `{"word":"serendipity"}`; it returns `translation`, `example`, and `mnemonic` strings. Gemini credentials are configured with `GEMINI_API_KEY` and are not needed when using the rest of the app without AI.

### ElevenLabs pronunciation

Pronunciation is generated by the Spring Boot backend through ElevenLabs' [Text to Speech endpoint](https://elevenlabs.io/docs/api-reference/text-to-speech/convert). The configured default model is `eleven_flash_v2_5`; model and voice availability depends on the ElevenLabs account. Set `ELEVENLABS_API_KEY` in the IntelliJ run configuration for `YuiApiApplication`. `ELEVENLABS_VOICE_ID` is optional when choosing a voice in **Settings**; `ELEVENLABS_MODEL_ID` can override the configured default model. Never put the API key in source files, `.env.example`, or the desktop `config.properties` file. The renderer never receives the key. The ElevenLabs key is sent only from the backend to their API.

In IntelliJ, open **Run → Edit Configurations… → YuiApiApplication**, then add the variables in **Environment variables** alongside the existing `DATABASE_PASSWORD`. You can enter `ELEVENLABS_API_KEY=your-key;ELEVENLABS_MODEL_ID=eleven_flash_v2_5`; optionally add `ELEVENLABS_VOICE_ID=your-default-voice-id`. Apply the change and restart the backend. Voice IDs available to the account can also be chosen in Yui's **Settings** panel; Yui stores that override locally.

The backend lists account voices with `GET /api/pronunciation/voices` (proxied to ElevenLabs' [List voices endpoint](https://elevenlabs.io/docs/api-reference/voices/search)) and generates audio with `POST /api/pronunciation`, for example `{"text":"incentive","voiceId":null}`. The MP3 response is stored in the user's data directory and keyed by text, voice, model, and output format. The packaged app uses `%APPDATA%\Yui\audio-cache`; direct IntelliJ runs default to `%USERPROFILE%\.yui\audio-cache` unless `YUI_TTS_CACHE_DIR` is set. Existing cache files are not packaged or removed by an app update.

For desktop runs, environment variables set only in the IntelliJ run configuration are not inherited by the packaged Yui app. Set `ELEVENLABS_API_KEY` as a Windows user environment variable for the installer, then fully restart Yui. The desktop launcher passes that variable to its backend process and keeps the generated MP3 cache in `%APPDATA%\Yui\audio-cache`. A user who controls the computer can inspect their own process and local files; this local backend does not make a shared API key safe for distributing to other people.

Manual API smoke check after configuring the key and voice (creates a temporary MP3):

```powershell
$body = '{"text":"incentive","voiceId":null}'
Invoke-WebRequest -Uri 'http://localhost:8080/api/pronunciation' -Method Post -ContentType 'application/json' -Body $body -OutFile "$env:TEMP\yui-pronunciation.mp3"
```

The `voiceId` may be omitted or set to `null` to use the backend default. In Yui, open **Settings**, choose an account voice, and use **Test voice**. The voice choice is stored locally in browser storage; audio bytes are cached separately by the backend.

### Windows desktop app

Yui can be run in an Electron window or installed from a custom Windows setup app. The setup app is a separate frameless Electron UI; it launches the embedded NSIS package silently to perform extraction, registration, upgrades, and uninstall. Electron serves the production Angular files from a loopback-only local server and proxies `/api` to a Spring Boot process bound to `127.0.0.1`. The renderer has Node integration disabled, context isolation enabled, and sandboxing enabled. A single-instance lock prevents multiple managed backend processes; the app stops only a backend process it started itself. It never starts or stops PostgreSQL.

#### Developer run

Install the frontend and desktop dependencies once:

```powershell
cd frontend
npm ci
cd ..\desktop
npm ci
```

Set `DATABASE_PASSWORD` in the current PowerShell session (and optionally `GEMINI_API_KEY`), then run `npm run dev` from `desktop`. The command starts Angular CLI and opens Yui in Electron. Electron uses a healthy API already running on port 8080, such as one launched from IntelliJ; otherwise it starts the backend with Maven. The existing Angular CLI and Maven workflows remain available independently.

#### Build the Windows installer

The build computer needs Windows, Node.js 22 or newer, Maven, and a full JDK 21 or newer with `jlink`. Install the Angular and Electron dependencies as above, then run:

```powershell
cd desktop
npm run build:windows
```

The script builds Angular and the Spring Boot JAR, creates a trimmed Java runtime from the build JDK, packages the NSIS install engine, and then wraps it in the custom 16:9 `Yui Setup.exe` application. The final installer is written to `desktop\release\Yui Setup <version>.exe`. Its progress indicator is intentionally indeterminate: silent NSIS does not expose reliable byte-level progress to the setup UI. The installed app includes its Java runtime, so end users do not need Java, Maven, Node.js, Angular CLI, or IntelliJ.

#### PostgreSQL and local settings

PostgreSQL remains a separate service and must already be installed and running on the computer. Create or use the existing `wordstead` database and `wordstead` database user; Yui does not bundle, migrate, start, stop, or remove PostgreSQL. Existing cards, review history, and FSRS state stay in that database and are not moved or deleted by the installer. The `DATABASE_URL`, `DATABASE_USER`, and `GEMINI_MODEL` settings are in `%APPDATA%\Yui\config.properties`, created at first launch. Set `DATABASE_PASSWORD` as a Windows user environment variable. `GEMINI_API_KEY` is optional and must also be configured as a Windows user environment variable; it is never bundled with the app. Desktop-launched apps do not inherit environment variables set only in an IntelliJ run configuration. After changing Windows environment variables, restart Yui.

Yui writes `desktop.log` and `backend.log` to `%APPDATA%\Yui\logs`. If PostgreSQL is unavailable or credentials are incorrect, the app shows a startup error and the backend log contains the database connection details. User settings and database contents are kept when the app is uninstalled. The un-signed installer may display a Windows SmartScreen warning; code signing is not configured.

Deck endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/decks` | List decks, most recently updated first |
| `GET` | `/api/decks/{id}` | Read one deck |
| `POST` | `/api/decks` | Create a deck |
| `PUT` | `/api/decks/{id}` | Replace a deck's name, description, and desired retention |
| `DELETE` | `/api/decks/{id}` | Delete a deck |

Create a deck with `Invoke-RestMethod -Method Post -Uri http://localhost:8080/api/decks -ContentType 'application/json' -Body '{"name":"Travel English","description":"Words for travelling"}'`.

Each deck response includes `cardCount` and `desiredRetention` (default `0.9`, configurable from `0.70` to `0.97`). Cards belong to one deck and are deleted with it. Card endpoints:

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/decks/{deckId}/cards` | List cards in a deck; optionally filter with `?query=word` |
| `GET` | `/api/decks/{deckId}/cards?dueOnly=true` | Return up to 100 due cards (optional `limit`, maximum 500); includes new and learning cards |
| `GET` | `/api/decks/{deckId}/cards/{cardId}` | Read one card |
| `POST` | `/api/decks/{deckId}/cards` | Create a card |
| `PUT` | `/api/decks/{deckId}/cards/{cardId}` | Replace a card's content |
| `DELETE` | `/api/decks/{deckId}/cards/{cardId}` | Delete a card |
| `POST` | `/api/decks/{deckId}/cards/{cardId}/reviews` | Submit one review rating |

Card fields are `front` and `back` (required), plus optional `example`, `mnemonic`, and `notes`. For example:

```json
{
  "front": "to board",
  "back": "wsiadać",
  "example": "We board at gate 4.",
  "mnemonic": "",
  "notes": null
}
```

The study interface submits exactly one of two answers with a client-generated idempotency UUID:

```json
{
  "submissionId": "a7fdc927-d670-40e1-9873-418f2ae20991",
  "answer": "REMEMBERED",
  "studySessionId": "96b1c77d-d391-47e8-9797-dd262ee72dce"
}
```

`REMEMBERED` maps on the backend to FSRS `GOOD` (3); `NOT_REMEMBERED` maps to `AGAIN` (1). The browser sends the binary answer and a Study session ID. The backend maps the answer before invoking FSRS-6, and review history stores the actual FSRS rating (`GOOD` or `AGAIN`). The scheduler still implements all four FSRS grades; the UI intentionally does not expose `HARD` or `EASY`. This makes review simpler, but removes the learner's ability to distinguish a difficult correct recall from an effortless one, so FSRS receives less nuanced feedback and uses only grades 1 and 3 for user reviews. After `AGAIN`, FSRS schedules its relearning step (currently ten minutes) without changing the due timestamp for session retries. Study puts the card at the back of the active session queue and allows another explicit rating only in the same session after a recorded `AGAIN`; merely showing the card does not submit another review. Outside that session, reviews remain blocked until `dueAt`. Each explicit answer has its own idempotency ID, and the session ID is recorded in review history for retry validation. A remembered card leaves the retry queue for the rest of that session, including during automatic due-list refreshes.

The API schedules reviews with FSRS-6 using the official default 21 parameters, a 90% default desired retention, one- and ten-minute learning steps, and a ten-minute relearning step. Date-based `REVIEW` due dates are shown at 00:00 in `Europe/Warsaw`, while timestamps are stored as UTC instants; consequently, the wall-clock wait can be shorter than the full FSRS day interval. For a never-reviewed new card, the first `GOOD` graduates it to `REVIEW` at midnight at the start of the next Warsaw calendar day. The same rule applies when a card is still in `LEARNING` and its latest review was `AGAIN`: the next `GOOD` graduates it to the next day's midnight instead of advancing to the 10-minute learning step. Native FSRS learning-step behavior would advance that card to its second learning step; this explicit business rule skips that remaining step. FSRS still calculates stability and difficulty, and all subsequent intervals are calculated by FSRS and anchored to midnight on their scheduled local date. Minute-based `AGAIN` retries and relearning steps, other ratings, and cards outside these learning conditions keep their existing scheduling behavior. The Java scheduling service follows the Open Spaced Repetition [`py-fsrs` 6.3.2 reference algorithm](https://github.com/open-spaced-repetition/py-fsrs/blob/main/fsrs/scheduler.py) because the available Java library did not match its reference vectors. Fuzzing is disabled so due dates are reproducible. The scheduler is checked against the official [review-sequence test vector](https://github.com/open-spaced-repetition/py-fsrs/blob/main/tests/test_basic.py). A card and its review log are written in the same transaction; the card row is locked while scheduling, and resubmitting the same UUID with the same card, answer and session returns the original result. Reusing an idempotency UUID with a different card, answer or session returns a conflict. Existing cards are migrated as new and due immediately. Review history is removed when its card is deleted.

## Proposed MVP architecture

The application uses one Angular single-page application and one Spring Boot REST API. PostgreSQL stores decks and cards; migrations are managed by Flyway and database access uses Spring Data JPA. The API owns validation and business rules; the browser calls it over REST through the Angular development proxy (`/api` to port `8080`). AI requests go through the backend so provider credentials never reach the browser. Authentication and device sync are intentionally deferred.

```text
frontend/             Angular application
  src/app/            shell, API client, and feature areas
  public/             static assets
  package.json        frontend dependencies and commands
backend/              Spring Boot REST API
  src/main/java/       application, deck and card APIs, and persistence
  src/main/resources/  configuration and Flyway migrations
  src/test/java/       HTTP integration tests
compose.yaml           local PostgreSQL service
.env.example           local database configuration template
```

## Current limitations

- The Angular interface can create, edit, delete, browse, and search decks and cards through the API.
- Accounts and synchronization are not implemented; this remains a single-library application.
- Review scheduling uses official default FSRS-6 weights; custom parameter optimization and timezone-specific daily cutoffs are not implemented. Scheduling timestamps use UTC.
- Backend tests use H2; a live PostgreSQL 18 smoke test has also passed in the development environment.
- No account system or synchronization exists yet.
- No API keys or other secrets are required by the current frontend.

## Manual smoke check

1. From `frontend/`, run `npm ci` and `npm start`.
2. Open `http://localhost:4200/` and confirm the Yui dashboard renders.
3. Resize the browser to a narrow viewport and confirm the layout remains readable.
4. Start the installed PostgreSQL service, set `DATABASE_PASSWORD` for the backend, and check `/api/health`.
5. In the app, create a deck and add a card with a front, back, and example.
6. Open the deck, search for a word, edit the card, then delete it and confirm the deck's card count changes.
7. Reload the page and confirm saved decks and cards remain available.
8. From `frontend/`, run `npm run build` and `npm test`; from `backend/`, run `mvn test`.
